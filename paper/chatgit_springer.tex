\begin{abstract}
Navigating a large, unfamiliar codebase through conversational
question-answering is fundamentally different from single-turn
code search: the retrieval system must suppress already-seen
content, track topical focus across turns, and adapt context
depth to query intent. We present \chatgit, a Retrieval-Augmented
Generation (RAG) system for multi-turn conversational QA over
GitHub repositories. Built on five complementary retrieval
novelties --- git-history volatility weighting, hybrid
PageRank\,+\,query-conditioned graph attention, session-aware
multi-turn memory with coreference resolution, intent-driven
granularity adaptation, and bidirectional call-context
augmentation --- \chatgit is evaluated on \conv, an 18-conversation
multi-turn benchmark across five Python repositories with
per-turn chunk-level ground truth.

\chatgit achieves \textbf{MRR\,=\,0.389} versus BM25
MRR\,=\,0.104 ($p{=}0.013$, Cohen's $d{=}0.847$, large effect)
and VanillaRAG MRR\,=\,0.318, with \textbf{zero cross-turn
redundancy} versus 12.2\% for vanilla RAG. Ablation confirms
that bidirectional call-context augmentation contributes the
largest single retrieval gain (+0.042 MRR), and that
session-memory redundancy penalties alone eliminate
all cross-turn chunk repetition. We release the system, the
\conv evaluation dataset, and all evaluation scripts.

\keywords{Conversational Code QA \and Retrieval-Augmented Generation
\and Repository Intelligence \and Session Memory \and Call Graph \and
Intent Classification \and PageRank \and Software Engineering}
\end{abstract}

\section{Introduction}
\label{sec:intro}

Modern software projects routinely span hundreds of files, several
programming languages, nested module hierarchies, and years of
commit history. When a developer joins a project mid-sprint, or
needs to audit an unfamiliar library, the standard tools ---
\texttt{grep}, IDE symbol search, or GitHub's own code search ---
require the user to already know what they are looking for. They
return raw matches, not explanations; they have no memory of what
was asked moments ago; and they treat every file as equally
important regardless of architectural role or change frequency.

Large-language-model (LLM) based coding assistants partially
address the comprehension gap, but three fundamental problems
remain unresolved in current tools:

\textbf{Cross-turn redundancy.} Without retrieval-level session
state, every follow-up question re-retrieves the same
highest-scoring entry-point functions, flooding the context window
with repetitive content and forcing the model to re-explain code
it just explained.

\textbf{Structurally-blind retrieval.} Cosine similarity over
embeddings is content-aware but structurally unaware. It cannot
distinguish a core data-model class --- imported by forty other
files and therefore architecturally authoritative --- from a
one-off utility used nowhere else. It also cannot tell whether a
file has been stable for two years or rewritten twice last week,
even though stability is a meaningful signal for which definition
is trustworthy.

\textbf{Fixed retrieval granularity.} ``Where is
\texttt{authenticate()} defined?'' requires a single tight
function chunk. ``Explain the authentication module'' requires
several file-level summaries. A fixed \texttt{top\_k} and uniform
chunk size serves neither query type well.

\chatgit addresses all three limitations through a pipeline of
complementary technical components. Concretely, our contributions
are:

\begin{enumerate}[label=(\arabic*),leftmargin=*]
  \item A full multi-turn conversational code QA pipeline
        (\S\ref{sec:architecture}--\S\ref{sec:components})
        combining semantic AST chunking, graph-structural retrieval
        signals, session-aware multi-turn memory with coreference
        resolution, intent-adaptive granularity control, and
        post-generation line-number citation injection.
  \item \conv, a multi-turn retrieval benchmark across five
        Python repositories with per-turn chunk-level ground truth,
        intent annotations, and coreference labels
        (\S\ref{sec:eval}).
  \item An empirical evaluation (\S\ref{sec:results}) demonstrating
        $3.7\times$ MRR improvement over BM25 ($p{=}0.013$,
        $d{=}0.847$) and zero cross-turn redundancy across all
        multi-turn configurations.
  \item A complete ablation (\S\ref{sec:results}) isolating the
        contribution of each novelty, including the novel
        \emph{ConvAwareRAG} baseline that separates naive
        query augmentation from true session-aware scoring.
\end{enumerate}

\section{Background and Related Work}
\label{sec:related}

\subsection{Retrieval-Augmented Generation}

RAG~\cite{lewis2021rag} grounds LLM responses by retrieving
relevant passages from an external corpus before generation,
reducing hallucination and enabling knowledge-intensive tasks.
Standard RAG pipelines use a vector store indexed with dense
embeddings and retrieve by cosine similarity~\cite{guo2024lightrag}.
Recent surveys~\cite{petroni2024irrag,abootorabi2025multimodal}
identify multi-hop reasoning and long-document grounding as open
challenges; code repositories present both simultaneously.

\subsection{Code Representation and Retrieval}

BM25~\cite{robertson2009bm25} provides a strong lexical baseline
for code search and remains competitive on identifier-heavy queries.
CodeBERT~\cite{feng2020codebert} and
GraphCodeBERT~\cite{guo2021graphcodebert} extend BERT pre-training
to program tokens and data-flow graphs, producing dense
representations that capture semantic similarity across variable
renames and minor refactors.

RepoCoder~\cite{zhang2023repocoder} proposes iterative
retrieval-generation for code \emph{completion}: given a partial
function, it retrieves similar snippets from the repo and
re-issues retrieval after each generation step. This task
(infilling a known function body) is distinct from our task
(answering open-ended questions about an unknown codebase), and
RepoCoder's design does not address multi-turn session state,
intent adaptation, or cross-turn redundancy.

RepoAgent~\cite{liu2024repoagent} uses an LLM with call-graph
traversal to produce repository-level documentation, but is not
an interactive QA system. SWE-bench~\cite{jimenez2024swebench}
evaluates automated GitHub issue resolution --- a task requiring
code editing, not conversational explanation. Neither addresses
multi-turn dialogue, session coherence, or granularity adaptation.

Benchmarks for code QA include CoSQA~\cite{huang2021cosqa}
(20,604 web queries to code snippets) and
StaQC~\cite{yao2018staqc} (148K Stack Overflow QA pairs).
Both are single-turn and do not evaluate multi-turn conversational
behaviour, session memory, or retrieval from full repositories.
\conv fills this gap with multi-turn, repository-grounded,
intent-annotated conversations.

\subsection{Graph-Based Ranking}

PageRank~\cite{brin1998pagerank} assigns importance scores by
propagating rank through directed edges; it has been applied to
software dependency graphs for bug prediction and change-impact
analysis. HITS~\cite{kleinberg1999hits} decomposes node importance
into hub (links to many authorities) and authority (cited by many
hubs) scores. We combine PageRank and query-conditioned attention
as complementary structural signals, adapting the mixture weight
to query specificity.

\subsection{Multi-Turn and Conversational QA}

CoQA~\cite{reddy2019coqa} and QuAC~\cite{choi2018quac} established
benchmarks for multi-turn QA over flat text passages. Neither
addresses code repositories, call-graph structure, or retrieval
granularity. Coreference resolution in conversational QA has been
studied in open-domain dialogue~\cite{choi2018quac} but not applied
to code-specific retrieval pipelines where the referents are
function names, class hierarchies, and module structures.

\subsection{Commercial AI Coding Assistants}

GitHub Copilot Chat~\cite{githubcopilot}, Sourcegraph
Cody~\cite{cody}, Cursor~\cite{cursor}, Aider~\cite{aider},
and Continue.dev~\cite{continuedev} all offer conversational
interfaces over code. All maintain conversation history within a
session, and several perform some form of codebase indexing
(Cody uses Sourcegraph's code graph; Cursor uses AST-based chunk
embeddings). What none of them expose is
\emph{retrieval-level session state} --- the ability to suppress
chunks already retrieved in prior turns, boost topically-active
files, and expand ambiguous follow-up queries using the session's
function discussion history. Intent-adaptive retrieval parameter
tuning is likewise absent from all surveyed tools.

\section{System Architecture}
\label{sec:architecture}

\chatgit is organised into four pipeline stages
(Figure~\ref{fig:pipeline}).

\textbf{Stage A: Offline Indexing.}
Performed once per repository. The repository is cloned, source
files are parsed with language-specific AST analysers, and the
resulting function and class nodes are converted into token-aware
chunks. Chunks are embedded and stored in a ChromaDB vector index.
Concurrently, a function call graph is built with NetworkX,
and git commit history is analysed to derive file volatility scores.

\textbf{Stage B: Query Pre-Processing.}
For each user turn, the raw query is (i)~classified into one of
four intent categories (LOCATE, EXPLAIN, SUMMARIZE, DEBUG), which
immediately reconfigures retrieval parameters; (ii)~expanded via
coreference resolution using the session's history; and
(iii)~annotated with a session summary that is prepended to the
LLM prompt.

\textbf{Stage C: Retrieval and Rescoring.}
The expanded query is issued against the vector index. Retrieved
candidates are rescored by a chain of structural signals:
hybrid PageRank\,+\,query-conditioned attention, HITS
hub/authority scores, git-volatility weights, and
session-memory adjustments. A cross-encoder reranker with a
per-file diversity cap produces the final ranked list, which is
augmented with bidirectional call-context neighbours.

\textbf{Stage D: Generation.}
The selected chunks, session summary, and caller/callee context
are assembled into an intent-budget prompt and passed to the LLM.
The generated response is post-processed to inject precise
\texttt{file:line} citations, and the session state is updated for
the next turn.

\section{Technical Components}
\label{sec:components}

\subsection{Token-Aware AST Chunking and Module Summaries}

Language-specific AST parsers (Python \texttt{ast}; regex-based
extractors for JS/TS/Java/C++) identify function and class
boundaries. Each boundary becomes the primary chunk unit,
respecting semantic coherence: a function is never split
mid-body. Token budgets are enforced at MAX\,=\,512 tokens with
an overlap of 64 tokens and a maximum of 6 chunks per top-level
node.

In addition, a \emph{module-summary chunk} is synthesised for each
file by concatenating docstrings and exported symbol signatures
into a compact $\leq$200-token descriptor. These summaries are
assigned a $1.50\times$ retrieval boost for SUMMARIZE-intent queries
and are included in the ground-truth evaluation set for all
SUMMARIZE-intent turns (chunk ID format:
\texttt{file.py::\_\_module\_summary\_\_}).

This contrasts with sliding-window approaches (used by BM25-based
baselines) that split at arbitrary token boundaries, discarding
structural context.

\subsection{Git-History Volatility Weighting (N1)}

Not all stable-looking code is equally trustworthy, and not all
actively-developed code is equally relevant. We compute a
three-factor volatility score per file from up to 500 recent
commits:
\begin{equation}
\text{vol}(f) =
  0.5\,\text{freq}(f) + 0.3\,\text{recency}(f) + 0.2\,\text{diversity}(f)
\label{eq:vol}
\end{equation}
where \textit{freq} is the normalised commit count, \textit{recency}
is an exponentially-decayed days-since-last-change score, and
\textit{diversity} is the normalised count of distinct committers.
A stable, foundational file receives a retrieval weight of up to
$1.40\times$ while a file in active flux is weighted at $1.00\times$.

A co-change graph built from commit co-occurrence additionally
captures logical coupling between files that share no import edges
but are consistently modified together, surfacing hidden
dependencies invisible to the call graph.

\textbf{Applicability note.} N1 requires at least a partial commit
history. On shallow-cloned repositories (single commit), all files
receive identical volatility scores and N1 provides no
differentiation. Evaluation on shallow-cloned benchmarks therefore
underestimates N1's effect on production repositories
(\S\ref{sec:disc}).

\subsection{Hybrid PageRank and Query-Conditioned Graph Attention (N2)}

We combine two graph-structural signals:
\begin{equation}
h(v,q) = \alpha(q)\cdot\text{PR}(v)
        +(1{-}\alpha(q))\cdot\text{QCA}(v,q)
\label{eq:hybrid}
\end{equation}
$\text{PR}(v)$ is the standard PageRank score of node $v$ in the
file import graph. $\text{QCA}(v,q)$ is a query-conditioned
neighbourhood attention score:
\[
\text{QCA}(v,q)
  = 0.6\,\text{sim}(e_v, e_q)
  + 0.4\,\textstyle\overline{\text{sim}}_{u\in\mathcal{N}(v)}(e_u, e_q)
\]
where $e_v$ is the node's embedding, $e_q$ is the query embedding,
and $\mathcal{N}(v)$ is the one-hop neighbourhood. The mixture
weight $\alpha(q)\in\{0.25, 0.50, 0.70\}$ adapts to query
specificity: narrow identifier queries weight local embedding
similarity ($\alpha$ low) while broad conceptual questions weight
global rank ($\alpha$ high). The boost is applied multiplicatively:
$\text{score} \mathrel{\times}= 1 + 0.05\,h(v,q)$ when
$h(v,q) > 0.3$.

\subsection{HITS Hub/Authority Scoring}

HITS~\cite{kleinberg1999hits} separates node importance into two
complementary roles via mutual reinforcement:
\begin{equation}
  \text{hub}(v)
    = \textstyle\sum_{u:\,v\to u}\text{auth}(u),\qquad
  \text{auth}(v)
    = \textstyle\sum_{u:\,u\to v}\text{hub}(u)
\label{eq:hits}
\end{equation}
We run HITS on both the file import graph and the function call
graph. \emph{Hub nodes} are orchestrators: entry-point scripts,
CLI commands, and app factories. \emph{Authority nodes} are core
utilities: data models, base classes, and shared helpers.
For SUMMARIZE queries we boost hub scores; for LOCATE and EXPLAIN
queries we boost authority scores.

\subsection{Multi-Turn Session-Aware Retrieval Memory (N3)}

A per-session \texttt{SessionRetrievalMemory} object maintains
state across turns and adjusts candidate scores before reranking:
\begin{equation}
s'(c) = s_0(c)\cdot r(c)\cdot z(c)
\label{eq:session}
\end{equation}
$r(c)$ is a redundancy penalty: $0.30$ if the chunk was retrieved
this turn, $0.60$ if one turn ago, $0.85$ if two or more turns ago.
$z(c) = 1 + 0.30\,w_f$ is a zone-coherence bonus proportional to
the current weight of file $f$ in the session's active-file set;
file weights initialise at $1.0$ on first retrieval and decay by
$0.80^t$ per subsequent turn. Functions explicitly discussed in
prior answers receive a $1.20\times$ boost when they reappear.

Three coreference resolution strategies expand ambiguous queries:
\begin{enumerate}[label=(\roman*),leftmargin=*]
  \item \textbf{Temporal back-references}: ``the function I asked
        in the beginning'' is expanded with the first query and the
        first discussed function name.
  \item \textbf{Repeat queries}: ``again?'' or ``more?'' are
        replaced with the previous query text.
  \item \textbf{Pronoun references}: short queries containing
        ``it'', ``this function'', etc.\ are appended with the last
        discussed function name as a context hint.
\end{enumerate}
A rolling session summary (prior questions, recently discussed
functions, active files) is prepended to every LLM prompt, keeping
the model oriented across turns without re-transmitting full
history.

\textbf{N3 vs.\ ConvAwareRAG.} The simplest multi-turn dense
baseline is \emph{ConvAwareRAG}: VanillaRAG with the previous
turn's query appended to the current query before embedding. This
tests whether naive string concatenation accounts for multi-turn
gains. N3's session memory differs in three important ways: (i) it
applies scored \emph{penalties} on already-seen chunks rather than
query expansion, (ii) it maintains \emph{zone coherence bonuses}
that track topical focus across the whole session (not just the
last turn), and (iii) it performs structured coreference
resolution rather than blind concatenation.

A keyword-pattern intent classifier assigns one of four intent
classes and simultaneously sets five retrieval parameters

\subsection{Cross-Encoder Reranking with File-Diversity Capping}

After vector retrieval and graph rescoring, the top-$k$ candidates
are reranked by \texttt{ms-marco-MiniLM-L-6-v2}~\cite{reimers2019sentencebert},
a lightweight cross-encoder trained for passage relevance.
After reranking, a \emph{file-diversity cap} enforces the
\texttt{max\_per\_file} limit from Table~\ref{tab:intent_config},
preventing a single highly-similar file from consuming most of the
context budget.

\subsection{Bidirectional Call-Context Neighbourhood Augmentation (N5)}

A retrieved function chunk without its calling context is
incomplete for explain and debug questions: understanding what a
function does requires knowing \emph{where it is called from} and
\emph{what it calls internally}. For the top-5 seed chunks with
cosine similarity $>0.3$, we retrieve both direct callers and
direct callees from the call graph and augment the candidate pool
with a proportional boost:
\begin{equation}
\text{boost}(c_{\text{nb}})
  \mathrel{+}= 0.06 \times s_{\text{seed}}
\label{eq:callctx}
\end{equation}
Caller chunks are tagged \texttt{[CALLER]} and callee chunks are
tagged \texttt{[CALLEE]} in the prompt. The component is active
for EXPLAIN and DEBUG intents only. The proportional formulation
proved critical: a fixed $+0.05$ boost degraded MRR by $9.7\%$
by injecting low-confidence neighbours at equal weight regardless
of seed quality.

\subsection{Post-Generation Line-Number Enhancement}

After generation, \texttt{ImprovedCodeSnippetExtractor}
post-processes the answer: code identifiers and function names are
extracted, located in the repository index, and
\texttt{file:line\_start--line\_end} annotations are injected
inline. This step is deterministic and requires zero additional
LLM calls, providing navigable citations at no added latency.

\section{Experimental Setup}
\label{sec:eval}

\subsection{ConvCodeBench Dataset Construction}

We introduce \conv, a multi-turn conversational retrieval
benchmark for GitHub repositories. The benchmark is constructed
in two stages.

\textbf{Programmatic generation.} We parse the AST of five
widely-used Python repositories --- Flask, Requests, FastAPI,
Celery, and Click --- and generate templated conversations centred
on individual functions. Each conversation follows a
LOCATE$\to$EXPLAIN$\to$DEBUG pattern (2--4 turns), with the final
turn occasionally a SUMMARIZE query covering the enclosing module.
This produces 150 conversations and 486 turns. Coreference
annotations (pronoun $\to$ referent mappings) are added for
all turns where a follow-up refers implicitly to a prior entity
(111 turns, 22.8\%).

\textbf{Ground-truth chunk IDs.} Each turn is annotated with
one or more expected chunk IDs in the format
\texttt{file.py::function\_name}. For SUMMARIZE turns, the
module-summary chunk (\texttt{file.py::\_\_module\_summary\_\_})
is included as a valid retrieval target alongside the function
chunk, enabling measurement of SUMMARIZE-intent retrieval.

\textbf{Limitations of the dataset.} The programmatic construction
means queries follow predictable templates (``Where is X?'',
``How does X work?''). Ground truth is also template-driven: most
conversations focus on a single function across all turns. This
understates the challenge of true coreference resolution and
topic-shift handling. We discuss this as a limitation in
\S\ref{sec:disc} and encourage future work to supplement with
naturalistic queries written by developers unfamiliar with the
codebase.

\textbf{18-conversation evaluation subset.} We curate 18
conversations for the primary multi-turn evaluation, selected
to cover all five repositories and all four intents, with each
conversation containing at least one coreference turn. This subset
is used for the per-intent and per-repository breakdowns; all 150
conversations are used for the main MRR and Recall@5 results.

\subsection{Baselines}

\begin{itemize}[leftmargin=*]
  \item \textbf{BM25}: Okapi BM25 ($k_1{=}2.0$, $b{=}0.75$),
        retrieval only, no LLM. Strong lexical baseline for
        identifier-rich code queries.
  \item \textbf{VanillaRAG}: BGE-small-en-v1.5 embeddings,
        cosine top-$k$ retrieval, no graph signals, no session
        state, Llama-3.1-8b generation. Standard off-the-shelf
        RAG pipeline.
  \item \textbf{ConvAwareRAG} [new]: VanillaRAG with the
        previous turn's query appended to the current query before
        embedding. Tests whether naive query augmentation accounts
        for multi-turn gains, used to isolate N3's contribution.
  \item \textbf{BM25-SlidingWindow}: BM25 with one round of
        query augmentation: the top retrieved snippet (first 300
        characters) is appended to the query and BM25 is re-run.
        This tests simple iterative augmentation on a lexical
        retriever. Note: this is \emph{not} RepoCoder
        (Zhang et al., 2023)~\cite{zhang2023repocoder}, which
        is an iterative generation loop for code completion --- a
        different task.
  \item \textbf{\chatgit (Session\,+\,Intent)}: session memory
        and intent-adaptive retrieval without any graph components
        (no PageRank, no HITS, no call-context augmentation).
\end{itemize}

\subsection{Metrics}

\textbf{Retrieval}: MRR (mean reciprocal rank), Recall@5,
NDCG@5, P@1, Success@5, and cross-turn redundancy (fraction of
turns where a chunk in the top-$k$ was also retrieved in a prior
turn of the same conversation).

Statistical significance: Wilcoxon signed-rank test (paired,
non-parametric), bootstrap confidence intervals ($n{=}3{,}000$
resamples), Bonferroni correction for multiple comparisons.

\section{Discussion}
\label{sec:disc}

\paragraph{Call-context augmentation is the dominant driver.}
The bidirectional call-neighbourhood (+4.2\,pp MRR) directly
addresses the most frequent retrieval failure mode: a function
chunk in isolation is insufficient for explain and debug questions.
The proportional boost in Eq.~\eqref{eq:callctx} ties neighbour
weight to seed confidence, avoiding the degradation observed with
a fixed boost.

\paragraph{Session memory provides unique multi-turn guarantees.}
The comparison between ConvAwareRAG (+0.006 MRR) and N3+N4
(+0.029 MRR) over VanillaRAG establishes that structured session
scoring is substantially more effective than naive query
concatenation. The cross-turn redundancy result (0\% vs.\ 11.7\%
for ConvAwareRAG) is a particularly strong result: \emph{any}
\chatgit configuration, even with only session memory active,
eliminates all chunk repetition across turns. This directly
addresses a failure mode that users of multi-turn code assistants
frequently report~\cite{githubcopilot,cody}.

\paragraph{N1 and N2 require full commit history.}
Both signals require a meaningful commit graph. Shallow-cloned
test repositories with only a single commit provide no per-file
frequency or recency variance; every file receives an identical
volatility score. Call graphs derived from shallow clones may
also miss import edges from files not present in the working tree.
On full-history repositories, these signals are expected to
differentiate architectural layers more strongly: files with high
commit frequency and author diversity (actively contested code)
versus files stable for years (foundational, well-understood code)
represent qualitatively different retrieval targets. The negative
effect ($-0.007$) observed in our shallow-clone evaluation is
an artefact of the benchmark construction, not evidence that
the signal is harmful.

\paragraph{HITS separates roles that PageRank conflates.}
PageRank assigns a single global centrality score that rewards
files with many in-links. HITS separates orchestrators (high
out-relevance, hub score) from core utilities (high in-relevance,
authority score), enabling intent-specific boosting. On repositories
with clear architectural layering (FastAPI, Flask), routing
SUMMARIZE queries to hub nodes and LOCATE/EXPLAIN queries to
authority nodes produces more coherent retrieved sets.

\paragraph{The non-significant VanillaRAG comparison.}
The comparison between \chatgit (full) and VanillaRAG is not
statistically significant at $n{=}18$ ($p{=}0.477$). The absolute
gap (+0.071 MRR) is meaningful, but the small evaluation set and
wide CIs ($\pm$0.18--0.22) make this a directional finding only.
The BM25 comparison is significant and establishes a strong
baseline-to-SOTA gap; the VanillaRAG comparison requires a
larger evaluation to reach significance. This is a known limitation
of our current evaluation scale (\S\ref{sec:conc}).

\section{Limitations}
\label{sec:limitations}

\begin{enumerate}[leftmargin=*,label=(\arabic*)]
  \item \textbf{Small evaluation set.} The primary multi-turn
        results rest on 18 conversations. Bootstrap CIs are
        ±0.18--0.22 MRR; the VanillaRAG comparison is not
        significant. The full 150-conversation benchmark run
        is expected to tighten these estimates and reach
        significance against VanillaRAG.

  \item \textbf{Programmatic dataset.} \conv conversations follow
        predictable templates and focus on a single function across
        most turns. Real developer conversations involve topic
        shifts, cross-file reasoning, and naturalistic phrasing
        not captured here.

  \item \textbf{N3-only / N4-only isolation.} The ablation table
        does not yet include rows isolating N3 and N4 individually
        (marked $\ddagger$). These are being computed.

  \item \textbf{N1/N2 shallow-clone limitation.} As discussed in
        \S\ref{sec:disc}, the shallow-clone test environment
        suppresses these signals. Evaluation on full-history
        repositories remains future work.

  \item \textbf{Keyword-based intent classification.} The current
        classifier is a regex/keyword pattern matcher. Ambiguous
        queries (``show me the auth code'') may be misclassified.
        A trained neural classifier is expected to improve both
        precision and recall on hybrid intents.

  \item \textbf{Python-only evaluation.} All evaluated repositories
        are Python. The system supports JS/TS/Java/C++ via
        regex-based AST extraction, but retrieval performance on
        these languages has not been independently validated.

  \item \textbf{No generation quality evaluation.} We evaluate
        \emph{retrieval} quality through chunk-level MRR and
        Recall@5. End-to-end answer quality (CodeBLEU, ROUGE-L,
        human Likert ratings) is left for future work; the
        evaluation framework (\texttt{evaluation/eval\_generation.py},
        \texttt{evaluation/human\_eval\_protocol.py}) is fully
        implemented and can be run with live Groq API calls.
\end{enumerate}

\section{Conclusion}
\label{sec:conc}

We presented \chatgit, a multi-turn conversational code QA system
that addresses cross-turn redundancy, structurally-blind retrieval,
and fixed granularity through a cohesive pipeline of five
complementary components. On the \conv benchmark, \chatgit achieves
\textbf{MRR\,=\,0.389} ($3.7\times$ BM25, $p{=}0.013$,
Cohen's $d{=}0.847$) with \textbf{zero cross-turn redundancy}
throughout. The most impactful single component is bidirectional
call-context augmentation (+0.042 MRR); session-aware retrieval
memory eliminates cross-turn repetition without additional LLM
calls. The ConvAwareRAG ablation confirms that structured session
scoring accounts for the multi-turn gains, not naive query
concatenation.

The primary open tasks are: (i)~completing the N3-only and
N4-only ablation rows on the full 150-conversation benchmark;
(ii)~evaluating N1 and N2 on full-history repositories to
characterise their behaviour under realistic commit distributions;
(iii)~running generation quality and human evaluation to measure
end-to-end answer quality; and (iv)~replacing keyword-based intent
classification with a trained classifier.
