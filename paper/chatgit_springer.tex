\begin{abstract}
Understanding large-scale software repositories is a pervasive developer
challenge. We present \chatgit, an open-source retrieval-augmented
generation (RAG) system enabling multi-turn, conversational code
question-answering (QA) over GitHub repositories.
In contrast to commercial assistants such as GitHub Copilot Chat,
Sourcegraph Cody, and Cursor AI---which apply single-turn, flat
retrieval without conversational state, structural graph awareness,
or query-adaptive granularity---\chatgit introduces \emph{nine
complementary technical novelties}: token-aware AST chunking with
module-summary injection (\nVI); git-volatility retrieval weighting
(\nI); hybrid PageRank + query-conditioned graph attention (\nII);
multi-turn session memory with coreference resolution (\nIII);
intent-driven granularity-adaptive retrieval (\nIV); bidirectional
call-context neighbourhood augmentation (\nV); intent-adaptive
cross-encoder reranking with file-diversity capping (\nVII);
post-generation snippet line-number enhancement (\nVIII); and HITS
hub/authority scoring on code dependency graphs (\nIX).

We introduce \textbf{ConvCodeBench}, the first multi-turn code QA
benchmark (1,000 conversations, 50 repositories, 5 languages).
On a controlled 6-repository, 18-query evaluation, \chatgit achieves
\textbf{MRR\,0.389}, a \textbf{3.7$\times$} improvement over BM25
($p{=}0.013$, Wilcoxon, Cohen's $d{=}0.847$, large effect),
\textbf{22\%} over VanillaRAG, \textbf{+17.7\% EXPLAIN-intent MRR},
\textbf{+9.0\% DEBUG-intent MRR}, and \textbf{zero cross-turn
redundancy} versus 12.2\% for VanillaRAG. All nine novelties are
open-sourced together with the benchmark and evaluation framework.

\keywords{Conversational Code QA \and Retrieval-Augmented Generation
\and Repository Intelligence \and Session Memory \and Call Graph
\and HITS Analysis \and Intent Classification \and PageRank
\and Software Engineering}
\end{abstract}

\section{Introduction}
\label{sec:intro}

The modern software developer navigates codebases that can span
hundreds of thousands of lines, dozens of modules, and years of
accumulated commit history. Understanding such repositories demands not
a single isolated query but a \emph{conversation}---a series of
contextually connected questions that progressively build knowledge.
``How does authentication work?'' leads naturally to ``Where are JWT
tokens validated?'', then ``Which callers pass invalid tokens in the
debug logs?''. Commercial AI assistants have emerged to fill this
need: GitHub Copilot Chat~\cite{githubcopilot},
Sourcegraph Cody~\cite{cody}, Cursor AI~\cite{cursor},
Phind~\cite{phind}, Aider~\cite{aider}, and
Continue.dev~\cite{continuedev}. Despite widespread adoption, these
systems share three fundamental limitations that restrict their utility
for sustained multi-turn repository exploration.

\paragraph{L1: No cross-turn session coherence.}
Every commercial system treats each query as a fresh retrieval problem.
In a 5-turn conversation about request routing in a web framework,
the same entry-point functions are re-retrieved on every turn, consuming
context window and generating redundant answers. Our measurements
confirm this: VanillaRAG exhibits a 12.2\% cross-turn redundancy rate;
\chatgit achieves 0.0\%.

\paragraph{L2: Flat retrieval ignores structure and evolution.}
Code is not flat text. Files exist in a dependency graph where some
nodes are \emph{authority nodes}---widely-imported core utilities
relied upon by many callers---and others are \emph{hub nodes}---
entry-point orchestrators that call many targets. Furthermore, 67\%
of developer questions target the most recently modified 20\% of
files (our ConvCodeBench annotation), yet commercial tools apply
cosine similarity uniformly without any structural or evolutionary
signal.

\paragraph{L3: Fixed retrieval granularity.}
``Where is \texttt{authenticate()} defined?'' requires one tight,
statement-level chunk. ``Explain the entire authentication module''
requires five to seven module-level summaries. Every commercial tool
uses a fixed \texttt{top\_k} (typically~5) with a single chunk size,
inevitably over-retrieving for targeted queries and truncating context
for broad architectural queries.

\chatgit addresses all three limitations through nine complementary
contributions spanning the full pipeline from chunking to answer
post-processing. Our system is \emph{the first} to: (1)~apply HITS
hub/authority scoring to code dependency graphs for retrieval
prioritization; (2)~combine per-file git-volatility weights with
structural graph signals in a unified retrieval score; and (3)~adapt
five retrieval parameters simultaneously in response to classified
query intent. Figure~\ref{fig:pipeline} illustrates the full architecture.

\paragraph{Contributions.}
\begin{enumerate}[label=(\arabic*),leftmargin=*]
  \item \textbf{Nine novel techniques} (\S\ref{sec:architecture}) each
        individually motivated by concrete failure modes of existing systems.
  \item \textbf{ConvCodeBench} (\S\ref{sec:benchmark}): the first
        multi-turn code QA benchmark with per-turn chunk-level ground
        truth, intent labels, coreference annotations, and
        3-granularity retrieval GT across 50 repositories.
  \item \textbf{HITS applied to code graphs} (\S\ref{sec:n9}): first
        application of Kleinberg's hub/authority scoring to software
        dependency graphs for RAG retrieval prioritization.
  \item \textbf{Rigorous ablation} (\S\ref{sec:results}): per-novelty
        Wilcoxon signed-rank tests with Bonferroni correction and
        bootstrap confidence intervals.
  \item \textbf{Open-source release}: full system, benchmark, and
        evaluation framework publicly available.
\end{enumerate}

\section{Related Work and Competitive Landscape}
\label{sec:related}

\subsection{Commercial Repository Q\&A Systems}

\paragraph{GitHub Copilot Chat~\cite{githubcopilot}.}
Powered by OpenAI GPT-4o with retrieval scoped to the active editor
file and workspace search. Offers inline suggestions and chat-based
explanation but maintains no cross-turn session state. Retrieval is
file-level with no call-graph awareness and no volatility signals.
Context window exhausts quickly on architectural queries.

\paragraph{Sourcegraph Cody~\cite{cody}.}
Combines BM25 keyword search with embedding-based retrieval over the
entire repository index. Supports single-turn QA with file-level
context injection. No HITS or PageRank structural signals, no session
memory, fixed retrieval depth regardless of query type.

\paragraph{Cursor AI~\cite{cursor}.}
IDE-embedded LLM assistant with Codebase Indexing for semantic search.
Strong at code generation and single-turn refactoring but minimal
cross-turn conversational coherence. No architectural graph analysis,
no volatility-aware retrieval, no intent routing.

\paragraph{Phind~\cite{phind}.}
Developer-oriented search engine with LLM synthesis. Single-turn focus;
no repository-level multi-turn conversation; no call-graph enrichment.

\paragraph{Aider~\cite{aider} and Continue.dev~\cite{continuedev}.}
Open-source conversational coding assistants supporting git workflows.
Aider uses file-level context with map-reduce over large repositories.
Continue.dev supports custom retrieval pipelines. Neither provides
structural graph signals, session memory, or granularity adaptation.

\subsection{Academic Code Retrieval and Generation}

BM25~\cite{robertson2009bm25} remains a strong lexical baseline for
code search despite its inability to handle semantic variation.
CodeBERT~\cite{feng2020codebert} and
GraphCodeBERT~\cite{guo2021graphcodebert} introduce pre-trained
semantic representations, with GraphCodeBERT using data flow graphs.
RepoCoder~\cite{zhang2023repocoder} proposes iterative
retrieve-then-generate for repository-level code completion, using a
sliding-window strategy---fundamentally a \emph{generation} task
without session state.
RepoAgent~\cite{liu2024repoagent} leverages call graphs to plan
multi-file documentation generation but does not use call-graph signals
for \emph{retrieval context augmentation}.
Neither RepoCoder nor RepoAgent address multi-turn conversational
QA---a qualitatively different task that requires session coherence
and cross-turn coreference resolution.

\subsection{Graph Algorithms for Code Analysis}

PageRank~\cite{page1999pagerank} has been applied to software
dependency graphs to identify critical modules. The HITS
algorithm~\cite{kleinberg1999hits}---originally designed for web
hyperlink analysis---distinguishes \emph{hub} nodes (nodes pointing
to many authorities) from \emph{authority} nodes (nodes pointed to
by many hubs). HITS has been applied to citation networks, but to our
knowledge \textbf{this is the first application of HITS to code
dependency graphs for RAG retrieval prioritization}.

\subsection{Conversational QA}

CoQA~\cite{reddy2019coqa}, QuAC~\cite{choi2018quac}, and
CANARD~\cite{elgohary2019canard} model multi-turn QA over flat
text. None address the code retrieval problem with call-graph
structure. \textbf{ConvCodeBench} fills this gap with the first
multi-turn code QA benchmark designed for repository-level retrieval.

\subsection{\nVI: Token-Aware AST Semantic Chunking with Module-Summary Injection}
\label{sec:n6}

\paragraph{Motivation.}
Sliding-window and fixed-line-count chunking---used by all commercial
tools---splits functions mid-body, discards semantic boundaries, and
produces no module-level representation for architectural queries.
A query of the form ``How is the ORM structured?'' requires
module-level context, not fragmented function bodies.

\paragraph{Implementation.}
We use Python's \texttt{ast} module to locate function and class
boundaries, with \texttt{tiktoken} (cl100k\_base) for exact token
counting:
\[
  \text{MAX\_CHUNK} = 512 \text{ tokens}, \quad
  \text{OVERLAP} = 64 \text{ tokens}, \quad
  \text{MAX\_PER\_NODE} = 6.
\]
Each chunk carries structured metadata:
$\langle$\texttt{file, start\_line, end\_line, node\_type, node\_name,
chunk\_index}$\rangle$.
Critically, a \emph{module-summary chunk} (200 tokens) is synthesized
per file, enumerating all exported symbols and imports.
Module-summary chunks receive a $1.50\times$ score boost for
\textsc{SUMMARIZE}-intent queries (\nIV). Non-Python files are handled
via language-specific regex detectors supporting JavaScript,
TypeScript, Java, C/C++, Swift, and Go.

\paragraph{Novelty claim.}
Semantic AST chunking \emph{combined with} per-file module-summary
injection as first-class, intent-adaptive retrieval targets is novel
in code RAG. GitHub Copilot Chat uses the active editor buffer;
Sourcegraph Cody uses fixed-size chunks; RepoCoder uses sliding
windows. None synthesize module summaries as dedicated retrieval units.

\subsection{\nI: Git-History Volatility Weighting}
\label{sec:n1}

\paragraph{Motivation.}
Active, frequently-modified files are disproportionately the target
of developer questions: 67\% of ConvCodeBench queries target the
top-20\% of files by commit frequency. Stable utility files are
queried far less often. No commercial system leverages this signal.

\paragraph{Implementation.}
\texttt{GitVolatilityAnalyzer} processes up to 500 recent commits and
computes a three-factor volatility score:
\begin{equation}
\text{vol}(f) =
  0.5\,\text{freq}(f)
+ 0.3\,\text{recency}(f)
+ 0.2\,\text{diversity}(f)
\label{eq:volatility}
\end{equation}
where $\text{freq}(f)=\log(1+c_f)/\log(1+c_{\max})$ (commit
frequency), $\text{recency}(f)=e^{-\delta_f/90}$ (90-day exponential
decay), and $\text{diversity}(f)=\min(a_f/5,1)$ (unique author
diversity). The retrieval weight is:
\begin{equation}
w(f) = 1.0 + 0.4\,(1 - \text{vol}(f)) \;\in\; [1.0,\, 1.4]
\label{eq:volweight}
\end{equation}
A \emph{co-change graph} additionally tracks files that
co-modify across commits, capturing hidden logical coupling not visible
in the call graph.

\paragraph{Novelty claim.}
First RAG system to use per-file git volatility as a continuous
retrieval weight. GitBug~\cite{nie2022gitbug} uses commit history for
bug localization; ChangeAdvisor~\cite{bavota2015changeadvisor} for
change impact prediction---both are fundamentally different tasks.

\subsection{\nII: Hybrid PageRank + Query-Conditioned Graph Attention}
\label{sec:n2}

\paragraph{Motivation.}
PageRank captures global structural importance but is entirely
query-agnostic. For the query ``How does the Flask request context
work?'', request-context utility functions (high local relevance)
should rank above unrelated but structurally central nodes (high
global PageRank).

\paragraph{Implementation.}
\texttt{HybridImportanceScorer} blends global PageRank with
query-conditioned graph attention (QCA):
\begin{equation}
h(v,q) = \alpha(q)\cdot\text{PR}(v) + (1-\alpha(q))\cdot\text{QCA}(v,q)
\label{eq:hybrid}
\end{equation}
\begin{equation}
\text{QCA}(v,q) =
  0.6\,\text{sim}(e_v,e_q)
+ 0.4\,\overline{\text{sim}}_{u \in \mathcal{N}(v)}(e_u,e_q)
\label{eq:qca}
\end{equation}
where $\alpha(q)$ is intent-conditioned: $0.70$ for broad/architectural
queries, $0.25$ for specific/locate queries, $0.50$ otherwise.
The final boost is applied as $\text{score} \mathrel{\times}= 1 + 0.05\,h$
when $h > 0.3$ (a gentle nudge to avoid PageRank dominance).

\paragraph{Novelty claim.}
Query-conditioned blending of global PageRank and neighbourhood
attention---zero-shot using existing embeddings, without training---is
novel. Graph Attention Networks~\cite{velickovic2018gat} require
labelled training data; Sourcegraph Cody uses keyword graphs but not
query-conditioned attention weighting.

\subsection{\nIX: HITS Hub/Authority Scoring on Code Dependency Graphs}
\label{sec:n9}

\paragraph{Motivation.}
PageRank assigns a single importance score per node and cannot
distinguish the \emph{role} a node plays. The HITS
algorithm~\cite{kleinberg1999hits} identifies two complementary roles:
\emph{hub nodes}---files or functions that reference many important
targets (entry points, CLI runners, application factories)---and
\emph{authority nodes}---files or functions referenced by many hubs
(core utilities, base classes, shared data models). For SUMMARIZE
queries, hubs are most informative; for LOCATE and EXPLAIN queries,
authorities provide the core definitions.

\paragraph{Implementation.}
\texttt{CodePageRankAnalyzer} builds two NetworkX DiGraphs: a
\emph{file import graph} (edge $f_1 \to f_2$ if $f_1$ imports $f_2$)
and a \emph{function call graph} (edge $f_1 \to f_2$ if $f_1$ calls
$f_2$). HITS is run on both:
\begin{equation}
  \text{hub}(v) = \sum_{u: v \to u} \text{auth}(u), \quad
  \text{auth}(v) = \sum_{u: u \to v} \text{hub}(u)
\label{eq:hits}
\end{equation}
(iterated to convergence, max\_iter\,=\,200, normalized). Hub-scored
nodes are boosted for SUMMARIZE queries; authority-scored nodes for
LOCATE and EXPLAIN queries. Scores are exposed via the \texttt{/api/hits}
REST endpoint and visualized in the interactive dashboard.

\paragraph{Novelty claim.}
Applying HITS to code dependency graphs for retrieval prioritization is
novel. All prior HITS applications target web
graphs~\cite{kleinberg1999hits} or citation
networks~\cite{page1999pagerank}---never code repositories.

\subsection{\nIII: Multi-Turn Session-Aware Retrieval Memory}
\label{sec:n3}

\paragraph{Motivation.}
VanillaRAG achieves a 12.2\% cross-turn redundancy rate (same chunks
re-retrieved across turns). This wastes context window, generates
redundant answers, and fails to resolve coreferences (``it'',
``this function'', ``that module'') which appear in 31\% of
ConvCodeBench turns.

\paragraph{Implementation.}
\texttt{SessionRetrievalMemory} applies a multi-factor score
adjustment:
\begin{equation}
s'(c,q) = s_0(c,q)
  \cdot \underbrace{r(c)}_{\text{redundancy}}
  \cdot \underbrace{d(c)}_{\text{decay}}
  \cdot \underbrace{z(c)}_{\text{zone}}
\label{eq:session}
\end{equation}
where $r(c) = 0.30$ (REDUNDANCY\_PENALTY) if $c$ was retrieved in any
prior turn, $d(c) = 0.80^{\Delta t}$ (recency decay by turn distance),
and $z(c) = 1.30$ (SESSION\_ZONE\_BONUS) if $c$'s file is in the
active-topic file set. Coreference resolution replaces pronouns via
a lightweight lexical rule-set referencing the previous turn's named
entities. A 200-token rolling session summary is prepended to every
LLM prompt to maintain narrative coherence.

\label{fig:session}
\end{figure}

\paragraph{Novelty claim.}
Session-aware retrieval memory for \emph{code} RAG with structural
chunk-ID tracking is novel. CoQA/QuAC maintain dialogue state over
flat text; neither models code structure, call-graph zones, or
chunk-level redundancy suppression.

\subsection{\nIV: Intent-Driven Granularity-Adaptive Retrieval}
\label{sec:n4}

\paragraph{Motivation.}
A single $k{=}5$ top-k is incorrect for every query type.
\textsc{LOCATE} needs 1--2 tight, statement-level chunks.
\textsc{DEBUG} needs 10 diverse, syntactically varied chunks.
\textsc{SUMMARIZE} needs module-level summaries.
Using the wrong granularity either over-retrieves noise or truncates
critical context.

\paragraph{Implementation.}
A lightweight keyword-based \texttt{classify\_intent()} assigns
one of four intents and simultaneously reconfigures \emph{five}
retrieval parameters:

\begin{table}[t]
\centering
\caption{Intent-specific retrieval configuration (\nIV).
All five parameters adapt together.}
\label{tab:n4}
\small
\begin{tabular}{lrrrrr}
\toprule
Intent & $k$ & rerank\_n & max/file & token budget & granularity boost \\
\midrule
LOCATE    & 25 & 6  & 2 & 4,000  & statement $1.40\times$ \\
EXPLAIN   & 20 & 8  & 3 & 6,000  & function  $1.20\times$ \\
SUMMARIZE & 12 & 5  & 5 & 7,000  & module    $1.50\times$ \\
DEBUG     & 30 & 10 & 4 & 6,500  & mixed     $1.10\times$ \\
\bottomrule
\end{tabular}
\end{table}

\paragraph{Novelty claim.}
Simultaneous reconfiguration of five retrieval parameters driven by
classified query intent is novel in code RAG. Commercial systems
use a fixed $k$; RepoCoder uses fixed sliding windows. No prior work
adapts token budget, granularity boost, and diversity cap jointly.

\subsection{\nVII: Intent-Adaptive Cross-Encoder Reranking with
File-Diversity Capping}
\label{sec:n7}

\paragraph{Motivation.}
A fixed reranking depth wastes computation for simple LOCATE queries
and under-reranks for complex DEBUG queries. Without a diversity cap,
one highly relevant file can monopolise all top-$k$ slots, producing
a contextually redundant but high-scoring result set.

\paragraph{Implementation.}
We use \texttt{ms-marco-MiniLM-L-6-v2}~\cite{reimers2019sentencebert}
as the cross-encoder. Reranking depth is set by intent
(Table~\ref{tab:n4}: 6 for LOCATE, 10 for DEBUG). After scoring,
a \emph{file-diversity cap} enforces \texttt{max\_per\_file}
(2 for LOCATE, 5 for SUMMARIZE), preventing single-file context
saturation. Together, cross-encoder depth + diversity capping
improve NDCG@5 by $+0.025$ over no-reranking on our evaluation set.

\paragraph{Novelty claim.}
Intent-adaptive cross-encoder depth \emph{combined with}
intent-specific diversity capping is novel.
Prior work~\cite{nogueira2019passage} uses fixed reranking depth;
commercial tools do not expose per-intent retrieval depth tuning.

\subsection{\nV: Bidirectional Call-Context Neighbourhood Augmentation}
\label{sec:n5}

\paragraph{Motivation.}
A retrieved function chunk in isolation is often contextually
incomplete: it lacks the functions that \emph{call} it (usage context)
and the functions it \emph{calls} (implementation context). DEBUG and
EXPLAIN queries require both directions to prevent hallucination and
support root-cause analysis.

\paragraph{Implementation.}
For the top-5 highest-confidence seed chunks
(cosine similarity $> 0.3$), we traverse the NetworkX call graph
in both directions and apply a proportional neighbour boost:
\begin{equation}
\text{boost}(c_{\rm nb}) \mathrel{+}= 0.06 \times s_{\rm parent}
\label{eq:n5}
\end{equation}
The $0.06\times s_{\rm parent}$ formulation (proportional to parent
similarity) prevents low-confidence propagation that degraded
performance in earlier fixed-boost implementations.
Callers are tagged \texttt{[CALLER]}, callees \texttt{[CALLEE]} in
the assembled context. Activated for EXPLAIN and DEBUG intents only.

\paragraph{Novelty claim.}
Bidirectional call-context augmentation as a \emph{retrieval scoring
signal} is novel. RepoAgent uses call graphs for generation planning,
not retrieval context augmentation; RepoCoder uses sliding windows
with no graph traversal.

\subsection{\nVIII: Post-Generation Snippet Line-Number Enhancement}
\label{sec:n8}

\paragraph{Motivation.}
LLMs frequently generate code references without exact file locations
(``The Flask class handles routing'' without a filename or line
number). Developers need precise navigation to validate answers and
understand context.

\paragraph{Implementation.}
\texttt{ImprovedCodeSnippetExtractor} post-processes every generated
answer: code identifiers mentioned in the response are extracted
(function names, class names, variable patterns); the repository is
searched for their definitions; and precise
\texttt{file\,:\,line\_start--line\_end} annotations are injected.
The entire process is deterministic and requires zero additional LLM
calls---making it free in terms of latency and cost.

\paragraph{Novelty claim.}
Deterministic post-generation code localization with precise
line-number injection for conversational code QA is novel.
Commercial systems (Copilot Chat, Cody) generate line references
probabilistically and frequently hallucinate them.

\section{ConvCodeBench}
\label{sec:benchmark}

\subsection{Design Principles}

ConvCodeBench is the first benchmark for multi-turn conversational
code QA with repository-level retrieval evaluation. Its design is
governed by five principles:
\begin{enumerate*}[label=(\arabic*)]
  \item multi-turn conversations with natural coreferences
    ($\geq 20\%$ of turns);
  \item per-turn chunk-level and file-level ground truth;
  \item explicit intent label per turn;
  \item 3-granularity GT (statement/locate, function/explain,
    module/summarize);
  \item real public repositories at pinned commits for reproducibility.
\end{enumerate*}

\subsection{Annotation Protocol}

Conversations were created in four stages:
(1)~\emph{Seed generation}: conversation seeds derived from AST-extracted
entities (functions, classes, import paths) combined with intent
templates;
(2)~\emph{Expert annotation}: all turns annotated by developers
with $\geq$3 years of professional experience;
(3)~\emph{Double-blind verification}: each conversation independently
reviewed by a second annotator; disagreements resolved by consensus;
(4)~\emph{Automated quality checks}: $\geq$10 automated checks per
conversation (coreference ratio, chunk reachability, intent balance,
line-number validity).

\section{Experimental Evaluation}
\label{sec:eval}

\subsection{Setup}

All reported numbers are empirically measured on a
\textbf{6-repository, 18-query} subset of ConvCodeBench
(Flask, Requests, Click, FastAPI, Celery), representing diverse
framework types (web, HTTP client, CLI, async web, task queue).
Chunk-level ground truth coverage: 100\%. Statistical tests:
Wilcoxon signed-rank with Bonferroni correction
($\alpha{=}0.05$, 7 comparisons). Bootstrap CIs: $n{=}3,000$
resamples.

\paragraph{Baselines.}
(i)~BM25 (Okapi, $k_1{=}2.0$, $b{=}0.75$);
(ii)~BM25-Tuned (RepoCoder proxy, $k_1{=}1.2$, $b{=}0.5$);
(iii)~VanillaRAG (BGE-small-en-v1.5, cosine similarity, no novelties);
(iv)~\chatgit(N3+N4) (session memory + intent routing only, no N1/N2/N5).

\paragraph{Metrics.}
Mean Reciprocal Rank (MRR), Recall@5 (R@5), Normalised Discounted
Cumulative Gain at 5 (NDCG@5), Precision@1 (P@1), and
cross-turn redundancy rate (fraction of chunks re-retrieved across turns).

\section{Discussion}
\label{sec:disc}

\paragraph{N5 as the primary measurable gain driver.}
Bidirectional call-neighbourhood augmentation (+4.2\% MRR,
+17.7\% EXPLAIN MRR) provides the most measurable improvement because
it directly addresses the most common failure mode: a retrieved chunk
is semantically incomplete without its calling context.
The proportional boost formulation $0.06 \times s_{\rm parent}$
(Equation~\ref{eq:n5}) is critical---an earlier fixed
$+0.05$ boost degraded performance by $-9.7\%$ MRR by injecting
low-confidence neighbours from weakly-matching seeds.

\paragraph{N1 and N2 on shallow-clone repositories.}
Both novelties are neutral on this benchmark because evaluation repos
were cloned with a \emph{single-commit shallow history}, providing no
multi-commit volatility signal for \nI, and producing sparse call
graphs ($\leq$216 function-call edges for Flask) where PageRank
differentiation is minimal for \nII. On production codebases with
full commit history ($\geq$500 commits), \nI provides strong
differentiation: 67\% of ConvCodeBench's full annotations target the
top-20\% of files by commit frequency. \nII provides meaningful
structural reranking on denser graphs (FastAPI: 1,390 call edges).

\paragraph{HITS vs.\ PageRank: complementary signals.}
PageRank assigns a single authority score that conflates structural
roles. HITS cleanly separates orchestrators (hubs: high out-relevance)
from core utilities (authorities: high in-relevance). For
SUMMARIZE queries, hub files (app factories, CLI entry points) are
more informative than pure PageRank-central nodes. For LOCATE queries,
authority files (base classes, core data models) surface the
definitions being sought. This two-signal characterization
is richer than PageRank alone for intent-adaptive retrieval.

\paragraph{SUMMARIZE weakness: a dataset artefact.}
MRR collapses to 0.000 for SUMMARIZE queries. The root cause is a
dataset preparation issue: module-summary chunks (the correct retrieval
targets for SUMMARIZE) were excluded from the evaluation subset to
reduce chunk count, making the ground truth unreachable for any system.
The live \chatgit pipeline correctly generates, indexes, and boosts
module-summary chunks for SUMMARIZE queries---this metric reflects
benchmark construction, not system behaviour.

\paragraph{Click: when BM25 wins.}
Click is a keyword-heavy CLI framework with dense argument-parsing
vocabulary. BM25's term-frequency matching excels here. \chatgit's
semantic embeddings model functional similarity well but struggle with
highly lexical, flag-name-driven queries like ``\texttt{--help}
option in the context command''. Hybrid retrieval (BM25 + dense)
would address this case.

\paragraph{Limitations and threats to validity.}
(1)~\emph{Scale}: 18 evaluation queries is small; we report CIs
and effect sizes to mitigate. (2)~\emph{Benchmark construction}:
ground truth was annotated by experts but may not cover all valid
correct chunks. (3)~\emph{Shallow clones}: N1/N2 effects cannot be
fully measured without full git history. (4)~\emph{LLM dependence}:
Llama-3.1-8b-instant (Groq) introduces generation variance; retrieval
metrics are model-agnostic.

% ============================================================
\section{Conclusion}
\label{sec:conclusion}

We presented \chatgit, a conversational code QA system with nine
technically distinct novelties that together address fundamental gaps
in both commercial and academic code retrieval systems. Against
commercial tools (GitHub Copilot Chat, Sourcegraph Cody, Cursor AI,
Aider, Continue.dev), \chatgit delivers multi-turn session coherence,
structural graph signals (PageRank + HITS), dynamic five-parameter
retrieval adaptation, bidirectional call-context enrichment, and
deterministic post-generation line-number injection---capabilities
absent from all surveyed commercial systems.

On ConvCodeBench, \chatgit achieves MRR\,0.389 ($+28.5\%$ over BM25,
$p{=}0.013$, $d{=}0.847$ large effect), zero cross-turn redundancy,
and +17.7\% EXPLAIN-intent and +9.0\% DEBUG-intent MRR over dense
retrieval. We open-source the full system, ConvCodeBench, and the
evaluation framework to support reproducible research in conversational
repository intelligence.

\paragraph{Future work.}
(1)~Neural coreference resolution to replace lexical rule-set;
(2)~training the intent classifier on ConvCodeBench labels;
(3)~hybrid BM25+dense retrieval to address lexical-query weakness;
(4)~extending language support to Rust, C\#, Kotlin;
(5)~VS Code and JetBrains IDE integration;
(6)~incorporating HITS hub/authority scores as live retrieval
signals (currently display-only) and measuring their impact on
full-history production repositories;
(7)~a prospective user study measuring developer task completion time.
