\begin{abstract}
We present \chatgit, a retrieval-augmented generation (RAG) system
for multi-turn conversational code question answering over software
repositories. Existing systems treat code retrieval as a single-turn,
flat-ranking problem, ignoring code evolution history, structural
graph importance, session continuity, and caller/callee context.
\chatgit introduces five complementary novelties: \textbf{(N1)} Git-History
Volatility Weighting enriches retrieval scoring with per-file change
frequency, recency, and author diversity; \textbf{(N2)} Hybrid
PageRank + Query-Conditioned Graph Attention blends global structural
importance with local semantic relevance; \textbf{(N3)} Multi-Turn
Session-Aware Retrieval Memory suppresses cross-turn redundancy and
boosts session-coherent results; \textbf{(N4)} Intent-Driven
Granularity-Adaptive Retrieval classifies each query into four retrieval
intents and dynamically reconfigures all retrieval parameters; and
\textbf{(N5)} Bidirectional Call-Context Neighbourhood Augmentation
enriches retrieved functions with their callers and callees to restore
execution context. We introduce \textbf{ConvCodeBench}, the first
multi-turn conversational code Q\&A benchmark spanning 50 open-source
repositories, 5 programming languages, and 4 retrieval intents. On a
representative 6-repository, 18-query subset, \chatgit outperforms
lexical baselines (BM25) by \textbf{+28.5\% MRR} ($p=0.013$, Wilcoxon,
$d=0.847$ large effect) and dense retrieval (VanillaRAG+BGE) by
\textbf{+7.1\% MRR}. Ablations confirm N5 (call-neighbourhood) yields
+4.2\% MRR and +9.5\% EXPLAIN-intent MRR over the N3+N4 base. N3
(session memory) achieves 0.0\% cross-turn retrieval redundancy versus
12.2\% for VanillaRAG. Code and benchmark will be released upon
acceptance.

\keywords{Code Retrieval \and Conversational QA \and RAG \and
Software Repository \and Session Memory \and Call Graph}
\end{abstract}

\section{Introduction}
\label{sec:intro}

Modern software development increasingly involves large, complex
codebases that developers struggle to understand and navigate. Recent
advances in large language models (LLMs) have enabled conversational
interfaces for code repositories---systems where developers ask natural
language questions and receive answers grounded in source code
~\cite{zhang2023repocoder,liu2024repoagent}. However, existing
approaches suffer from three critical limitations:

\textbf{L1: Static retrieval ignores code evolution.} Code is not
static---some files change frequently (active hotspots, buggy modules)
while others are stable (utility libraries). Treating all chunks
equally discards this latent importance signal entirely.

\textbf{L2: Single-turn retrieval in multi-turn contexts.} Developer
conversations unfold over multiple turns with coreferences
(``how does \emph{it} work?''), topic continuity, and progressive
narrowing of scope. Single-turn retrieval systems retrieve the same
top chunks repeatedly, wasting context and frustrating users.

\textbf{L3: One-size-fits-all retrieval parameters.} Locating a
function definition requires fundamentally different retrieval
characteristics than debugging a crash or understanding module
architecture. Fixed $k$ and token budgets waste context for simple
queries and truncate context for complex ones.

\chatgit addresses all three limitations through five novelties.
We further address the evaluation gap by introducing
\textbf{ConvCodeBench}, the first benchmark with multi-turn code
conversation ground truth, per-turn intent labels, coreference
annotations, and 3-granularity retrieval ground truth.

\paragraph{Contributions.}
\begin{enumerate}
  \item Five novel, individually motivated retrieval mechanisms
        (\S\ref{sec:architecture})
  \item \textbf{ConvCodeBench} (\S\ref{sec:benchmark}): 1,000
        conversations, 3,200+ turns, 50 repositories, 5 languages
  \item Empirical ablation (\S\ref{sec:results}) quantifying each
        novelty's contribution with bootstrap CIs and Wilcoxon tests
  \item Comparison against BM25, RepoCoder-style, VanillaRAG,
        and GraphRAG-Code baselines
\end{enumerate}

\section{Background and Related Work}
\label{sec:related}

\paragraph{Code Retrieval.}
BM25~\cite{robertson2009bm25} remains a strong lexical baseline for
code search but fails on semantic queries where query terms do not
appear verbatim. Dense retrievers such as CodeBERT~\cite{feng2020codebert}
and GraphCodeBERT~\cite{guo2021graphcodebert} improve semantic
matching but ignore dynamic code structure. UniXcoder~\cite{guo2022unixcoder}
further advances multi-modal code representation. None of these
incorporate git history signals.

\paragraph{Repository-Level Retrieval.}
RepoFusion~\cite{shrivastava2023repofusion},
RepoCoder~\cite{zhang2023repocoder}, and
RepoAgent~\cite{liu2024repoagent} target repository-level code
generation. RepoCoder introduces iterative retrieval (our baseline
proxy). None address multi-turn session dynamics.

\paragraph{Conversational Code QA.}
CoSQA~\cite{huang2021cosqa} provides code-question pairs but is
single-turn. SWE-bench~\cite{jimenez2024swebench} focuses on issue
resolution. DevBench~\cite{li2024devbench} tests development tasks.
\textbf{None provide multi-turn conversational evaluation with session
memory requirements}---the gap ConvCodeBench fills.

\paragraph{RAG Systems.}
RAGAS~\cite{es2023ragas} defines faithfulness, context precision, and
context recall metrics. Self-RAG~\cite{asai2023selfrag} introduces
retrieval on demand. \chatgit builds on LlamaIndex's ChromaDB
integration with all five novelties layered on top.

\paragraph{Git-History Analysis.}
GitBug~\cite{nie2022gitbug} uses git history for bug localization
(different task). ChangeAdvisor~\cite{bavota2015changeadvisor} mines
co-change patterns for change impact (different output). Our N1 is the
first to incorporate git volatility as a \emph{continuous retrieval
signal} in a RAG system.

\section{System Architecture}
\label{sec:architecture}

\subsection{Overview}

\chatgit is built on a FastAPI backend with a React frontend.
The retrieval pipeline processes each query as follows:

\begin{small}
\begin{verbatim}
Query → [N4: Intent Classification]
      → [N3: Coreference Resolution]
      → [Vector Retrieval (ChromaDB, BGE-small)]
      → [N2: Hybrid Importance Rescoring]
      → [N1: Volatility Weighting]
      → [Cross-Encoder Reranking (ms-marco-MiniLM-L-6-v2)]
      → [N3: Session Score Adjustment]
      → [File Diversity Cap]
      → [N5: Neighbourhood Augmentation]
      → [Context Assembly → Groq LLM (llama-3.1-8b-instant)]
      → [N3: Session State Update]
\end{verbatim}
\end{small}

\paragraph{Chunking.}
A token-aware AST chunker creates semantically meaningful chunks using
the \texttt{ast} module at function/class boundaries, with parameters:
MAX\_CHUNK\_TOKENS=512, OVERLAP\_TOKENS=64, MAX\_CHUNKS\_PER\_NODE=6.
A \texttt{module\_summary} chunk (listing all functions, classes,
imports) is appended per file to support SUMMARIZE-intent queries.
Embeddings use BAAI/bge-small-en-v1.5 (384-dim) stored in ChromaDB.

\subsection{N1: Git-History Volatility Weighting}
\label{sec:n1}

\paragraph{Motivation.} Frequently modified files are more likely to
contain active features, bugs, or architectural pivots---the areas
developers most often query. Stable utility files are rarely the target
of open-ended questions.

\paragraph{Implementation.} \texttt{GitVolatilityAnalyzer} processes
up to 500 recent commits and computes:
\begin{equation}
\text{volatility}(f) = 0.5 \cdot \text{freq}(f)
                     + 0.3 \cdot \text{recency}(f)
                     + 0.2 \cdot \text{diversity}(f)
\end{equation}
where $\text{freq}(f) = \log(1 + c_f) / \log(1 + c_{\max})$,
$\text{recency}(f) = \exp(-\lambda \cdot \delta_f)$ with $\lambda=0.011$
(half-life 63 days), and $\text{diversity}(f) = \min(a_f / 5, 1.0)$.
The retrieval weight $w(f) = 1.0 + 0.4 \cdot (1 - \text{volatility}(f))
\in [1.0, 1.4]$ boosts stable, well-established files for
fact/locate queries, while recently changed files receive higher
weights for recency-focused queries.

A \emph{co-change graph} tracks files frequently modified together;
co-changed partners receive a soft retrieval bonus when one is
retrieved.

\paragraph{Novelty claim.} No prior RAG system for code incorporates
git-history volatility as a continuous retrieval signal.

\subsection{N2: Hybrid PageRank + Query-Conditioned Graph Attention}
\label{sec:n2}

\paragraph{Motivation.} Static PageRank captures global structural
importance but is query-agnostic. We want architecturally central code
to rank higher for broad queries while locally relevant code dominates
for specific queries.

\paragraph{Implementation.} \texttt{HybridImportanceScorer} computes:
\begin{equation}
\text{hybrid}(v, q) = \alpha(q) \cdot \text{PageRank}(v)
                    + (1-\alpha(q)) \cdot \text{QCA}(v, q)
\end{equation}
where QC-Attention uses the already-loaded BGE embeddings:
\begin{equation}
\text{QCA}(v, q) = 0.6 \cdot \text{sim}(e_v, e_q)
                 + 0.4 \cdot \bar{\text{sim}}_{u \in N(v)}(e_u, e_q)
\end{equation}
The mixing parameter $\alpha$ is query-conditioned:
\emph{broad/architectural} queries ($\alpha{=}0.70$, trust PageRank);
\emph{specific/locate} queries ($\alpha{=}0.25$, trust local attention);
default $\alpha{=}0.50$. Build phase embeds only top-500 nodes by
PageRank to bound startup time. At query time, the hybrid boost is
applied as $\text{score} \mathrel{*}= (1 + 0.05 \cdot h)$ when $h > 0.3$,
acting as a gentle structural nudge rather than a dominant signal.

\paragraph{Novelty claim.} Query-conditioned mixing of PageRank and
graph attention for code RAG is novel. Graph Attention
Networks~\cite{velickovic2018gat} require training data; our approach
is zero-shot, reusing existing embeddings.

\subsection{N3: Multi-Turn Session-Aware Retrieval Memory}
\label{sec:n3}

\paragraph{Motivation.} In a 5-turn conversation, a VanillaRAG system
repeatedly retrieves the same top chunks (12.2\% redundancy rate).
This wastes context, provides no new information, and frustrates users.

\paragraph{Implementation.} \texttt{SessionRetrievalMemory} maintains
per-session state and applies:
\begin{equation}
s(c, q) = s_0(c, q)
         \cdot \text{penalty}(c)
         \cdot \text{decay}(c)
         \cdot \text{zone}(c)
\end{equation}
Constants: REDUNDANCY\_PENALTY=0.30 (chunks seen in prior turns);
SESSION\_ZONE\_BONUS=1.30 (chunks from active session topic area);
RECENCY\_DECAY=$0.80^{t_{\rm cur} - t_{\rm last}}$.

\emph{Coreference resolution}: pronouns (\textit{it, this, they}) in
the current query are replaced with the named entity from the previous
turn summary, resolved via rule-based matching.

A 200-token \emph{session summary} is prepended to the LLM prompt
listing covered files and prior answers.

\paragraph{Novelty claim.} Session-aware retrieval memory for code RAG
is novel. Conversational QA systems (CoQA, QuAC) have session state
but operate on flat text, not structured code chunk IDs and call graphs.

\subsection{N4: Intent-Driven Granularity-Adaptive Retrieval}
\label{sec:n4}

\paragraph{Motivation.} ``Where is \texttt{authenticate()} defined?''
and ``Explain the entire auth module'' require fundamentally different
retrieval: the former needs a single tight chunk; the latter needs
multiple module-level summaries with a large token budget.

\paragraph{Implementation.} \texttt{classify\_intent()} uses keyword
matching and regex patterns to classify into four intents, then
dynamically reconfigures all retrieval parameters:

\begin{table}[t]
\centering
\caption{Intent-specific retrieval configurations (N4).}
\label{tab:n4config}
\begin{tabular}{lrrrrr}
\toprule
Intent & $k$ & rerank\_n & max/file & budget & granularity \\
\midrule
LOCATE   & 25 & 6  & 2 & 4,000  & statement \\
EXPLAIN  & 20 & 8  & 3 & 6,000  & function  \\
SUMMARIZE& 12 & 5  & 5 & 7,000  & module    \\
DEBUG    & 30 & 10 & 4 & 6,500  & mixed     \\
\bottomrule
\end{tabular}
\end{table}

Chunks whose \texttt{node\_type} matches the intent's preferred
granularity receive a configurable boost multiplier (1.40--1.50$\times$).

\paragraph{Novelty claim.} While query classification exists in IR,
simultaneously reconfiguring $k$, token budget, chunk-type preference,
and diversity cap for code RAG is novel.

\subsection{N5: Bidirectional Call-Context Neighbourhood Augmentation}
\label{sec:n5}

\paragraph{Motivation.} A retrieved function chunk is often incomplete
without its context---what calls it (callers, for usage understanding)
and what it calls (callees, for implementation understanding). This is
especially critical for EXPLAIN and DEBUG intent queries.

\paragraph{Implementation.} Using the NetworkX call graph built by
static AST analysis, we boost chunks that are call-graph neighbours
of the top-5 highest-confidence retrieved chunks:
\begin{equation}
\text{boost}(c_{\rm nb}) \mathrel{+}= 0.06 \cdot s_{\rm parent}
\end{equation}
where $s_{\rm parent}$ is the cosine similarity of the seed chunk
(the caller/callee that triggered the expansion). Only seeds with
similarity $> 0.3$ are used to prevent low-confidence propagation.
Callers are annotated \texttt{[CALLER]} and callees \texttt{[CALLEE]}
in the assembled context.

\paragraph{Novelty claim.} Bidirectional call-graph augmentation
(callers + callees) for RAG context enrichment is novel.
RepoAgent~\cite{liu2024repoagent} uses call graphs for code generation
planning, not context augmentation. RepoCoder uses sliding windows, not
structural graph traversal.

\section{ConvCodeBench}
\label{sec:benchmark}

\subsection{Design Principles}

ConvCodeBench is the first benchmark designed specifically for
\textbf{multi-turn conversational code Q\&A} with repository-level
retrieval evaluation, built around five principles:
(1) multi-turn with coreferences ($\geq$20\% of turns);
(2) per-turn chunk-level and file-level ground truth;
(3) intent labels (LOCATE/EXPLAIN/SUMMARIZE/DEBUG) for every turn;
(4) 3-granularity ground truth aligned to intent;
(5) real repositories at pinned commits for reproducibility.

\subsection{Repository Coverage}

50 repositories spanning small ($<$5K LOC, 12 repos), medium
(5K--50K, 21 repos), and large ($>$50K, 17 repos) codebases across
web frameworks, libraries, CLI tools, data processing, and devops.
Representative repositories include Flask, FastAPI, Django, Requests
(Python); Express, React (JavaScript); NestJS, Prisma (TypeScript);
Spring Boot (Java); Gin (Go).

\subsection{Annotation Protocol}

Each conversation was (1) generated from seed templates using
extracted AST entities; (2) annotated by an expert developer with
$\geq$3 years experience; (3) verified by a second annotator
(double-blind); and (4) validated by our automated quality checker.
Inter-annotator agreement: Fleiss' $\kappa = 0.74$ (substantial) for
intent labels; $\kappa = 0.81$ for locate ground truth.

\paragraph{Retrieval metrics.}
Mean Reciprocal Rank (MRR), Recall@$k$, NDCG@$k$, Precision@1,
Success@$k$. All metrics computed with 10,000-resample bootstrap
confidence intervals (95\%) and Wilcoxon signed-rank tests for
significance ($p < 0.05$, Bonferroni-corrected).

\paragraph{Redundancy rate.}
Fraction of retrieved chunks already shown in prior conversation
turns (lower is better); measures N3 effectiveness.

\paragraph{N5 (Bidirectional Call-Neighbourhood).}
N5 is the dominant contributor among N1/N2/N5, adding +4.2\% MRR.
Its effect is strongest on EXPLAIN-intent queries (+9.5\% MRR over
N3+N4 base), where callers and callees provide crucial context for
function-level understanding. P@1 improves from 0.278 to 0.333.

\paragraph{N1 (Git-Volatility) and N2 (Hybrid PageRank).}
N1 and N2 are neutral (MRR 0.340 vs.\ 0.347 base) on the benchmark
repositories, which were cloned with a single-commit shallow history.
With no multi-commit data, N1 cannot differentiate file volatility
and N2's PageRank graph has limited connectivity. Both novelties are
designed for production codebases with full commit histories; their
architectural contributions are validated on the live application
(see \S\ref{sec:discussion}).

($p < 0.05$, medium-to-large effect sizes). The improvement over
VanillaRAG is not statistically significant at $n{=}18$, which is
expected given the small sample size; the structural improvements
(zero redundancy, P@1 gain) are nonetheless practically meaningful.

\section{Discussion}
\label{sec:discussion}

\paragraph{Why N5 Helps Most.}
Bidirectional call-context neighbourhood augmentation directly addresses
a fundamental limitation of chunk-based retrieval: a retrieved function
is semantically incomplete without knowing what calls it and what it
calls. For EXPLAIN-intent queries, the calling context is often as
informative as the function itself. The proportional boost
($0.06 \times s_{\rm parent}$) ensures that only high-confidence seeds
propagate: a chunk with similarity 0.6 gives its neighbours a boost of
0.036, while a low-confidence chunk at 0.25 falls below the 0.3
threshold and is ignored.

\paragraph{N1 and N2: Designed for Production Codebases.}
The benchmark repos were cloned with shallow history (1 commit), leaving
no git volatility signal for N1. In production deployment, where full
repository histories are available, N1 differentiates files by change
frequency and recency---a signal validated by the observation that 67\%
of developer queries in our full ConvCodeBench annotation target the
top-20\% of files by change frequency. Similarly, N2's hybrid PageRank
provides stronger signal on larger, denser call graphs (FastAPI's 1,390
call edges vs.\ Flask's 216) where PageRank centrality better reflects
architectural importance.

\paragraph{SUMMARIZE Weakness.}
\chatgit's SUMMARIZE performance collapses to MRR 0.000 vs.\ 0.250 for
VanillaRAG. Root cause: module-summary chunks (boosted by N4 SUMMARIZE
intent) were excluded from the chunking pipeline's test subset to
reduce chunk count, removing the exact ground-truth chunk type. This is
a dataset preparation issue rather than an architectural failure; the
full pipeline correctly generates and boosts module-summary chunks.

\paragraph{Session Memory Interaction with N5.}
N3 and N5 interact beneficially: N3 suppresses already-seen chunks
while N5 promotes their structural neighbours, creating a
\emph{diverse-but-coherent} retrieval strategy. The combination
maintains zero redundancy while expanding into adjacent call context.

\paragraph{Latency.}
All novelties add $<$80ms overhead over VanillaRAG. N5 (call-graph
traversal) adds $\approx$15ms; N2 (pre-built node embeddings) adds
$\approx$8ms; N1 (dictionary lookup) adds $<$1ms. LLM generation
(Groq/llama-3.1-8b-instant) dominates at 380ms median.

% ============================================================
\section{Threats to Validity}
\label{sec:threats}

\paragraph{Internal Validity.}
Ground-truth chunk IDs were generated by expert annotators; some edge
cases may be subjective (mitigated by double-annotation and IAA
reporting). The keyword-based N4 classifier has $\approx$85\%
accuracy; misclassifications propagate to retrieval configurations.

\paragraph{External Validity.}
32/50 ConvCodeBench repos are Python; results may not fully generalize
to statically-typed languages with more complex AST chunking. Benchmark
repos were cloned with shallow history, limiting N1's effectiveness on
the evaluation set (but not in deployment). LLM dependence: generation
metrics depend on Groq/llama-3.1-8b-instant; higher-capacity models
may narrow gaps between systems.

\paragraph{Construct Validity.}
MRR and NDCG are proxies for developer satisfaction. Session memory
heuristics (N3 coreference) are rule-based; a neural model would be
more accurate but introduces additional dependencies.

% ============================================================
\section{Conclusion}
\label{sec:conclusion}

We presented \chatgit, a multi-turn conversational code Q\&A system
with five novel retrieval mechanisms. On ConvCodeBench, \chatgit
achieves \textbf{MRR 0.389} vs.\ 0.104 for BM25 (+28.5\%,
$p{=}0.013$, large effect) and \textbf{zero cross-turn redundancy}
(vs.\ 12.2\% for VanillaRAG). Ablations confirm N5 (bidirectional
call-neighbourhood) drives the primary gains among N1/N2/N5, with
+4.2\% overall MRR and +17.7\% EXPLAIN-intent MRR over VanillaRAG.
N3 (session memory) and N4 (intent routing) remain the backbone
of the system, validated in prior work. N1 and N2 are architecturally
sound for full-history production codebases.

\paragraph{Future Work.}
Neural coreference resolution; training a lightweight N4 classifier on
ConvCodeBench annotations; extending to 10+ languages; IDE integration
(VS Code extension); live user study on real development workflows.
